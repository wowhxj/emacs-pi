# 可编辑队列的交互与协议

## 当前边界

本机使用的 Pi 0.87.1 RPC 在 `queue_update` 中仅发送 steer 与 follow-up 的文本数组。`clear_queue` 只返回文本并一次清空两个队列；`prompt`、`steer`、`follow_up` 只能新增消息。队列中图片的二进制内容、稳定消息 ID 与修订号都不通过 RPC 提供。因此 emacs-pi 目前把队列作为只读列表；按 `C-c C-l` 查看，mode-line 用 `[S数量 F数量]` 提示。Emacs 本次发送且文本仍可匹配的图片可在列表中预览，不能据此推断所有消息的附件。

清空后逐条重发不能作为正式编辑实现：图片可能无法恢复，而且 Pi 正在运行时可能在清空与重发之间消费队列。遇到重复文本时，也无法证明哪一条携带图片。

## 目标交互

队列列表保留 steer 和 follow-up 两栏，每项显示顺序、完整文本摘要、附件缩略图/文件名和当前状态。焦点位于某项时：

| 按键 | 动作 |
| --- | --- |
| `RET` | 在独立编辑区修改该项文本与附件；`C-c C-c` 保存，`C-c C-k` 放弃 |
| `M-<up>` / `M-<down>` | 在同一栏上移 / 下移 |
| `s` / `f` | 转为 steer / follow-up，并放在目标栏末尾 |
| `d` | 删除该项 |
| `a` / `p` | 编辑时添加文件图片 / 粘贴剪贴板图片 |
| `x` / `r` | 编辑时移除 / 替换焦点图片 |
| `g` | 刷新列表 |

编辑区打开时保存原聊天草稿与图片，不覆盖输入区；失败或修订号冲突时保留编辑内容并刷新列表。缩略图只负责显示，保存必须保留原始图片数据。

## Pi RPC 所需合同

Pi 端必须维护稳定的队列 item ID 和单调递增的 `revision`。`get_queue` 返回 `revision` 与有序的 steer/follow-up 项；每项包含 `id`、`text`、附件的 `id`、名称、MIME 和尺寸。图片预览应通过独立的 `get_queue_image` 按附件 ID 获取，避免每次 `queue_update` 重复发送大块 base64。

`update_queue` 接收 `expectedRevision` 与单个操作：`edit`（文本和附件变更）、`move`（目标栏和位置）、`remove`。修改、队列消费与 revision 更新必须在 Pi 同一个序列化边界内完成。若 item 已消费或 revision 不符，返回冲突和最新快照，不执行部分操作。编辑图片时可引用该项原有附件 ID；新图片发送 MIME 与 base64。成功后返回新 revision 和队列快照，并发出 `queue_update`。编辑器不得用 `clear_queue` 加重发来模拟这些操作。

emacs-pi 在启动时探测此协议能力；不支持的 Pi 版本维持只读列表，不显示不能兑现的编辑按键。
